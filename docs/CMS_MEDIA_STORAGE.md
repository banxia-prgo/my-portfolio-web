# CMS media storage deployment

The API stores normalized image files and WebP thumbnails in `MEDIA_ROOT` (default: `/app/media`). This directory must be backed by persistent host storage before enabling uploads in production.

## Production server preparation

Create the host directory and restrict write access:

```bash
sudo install -d -o root -g root -m 0755 /var/lib/banxia/uploads
```

In the existing `api` service in `/opt/banxia-api/compose.yaml`, add this volume entry without changing the database service, ports, networks, or environment configuration:

```yaml
    volumes:
      - /var/lib/banxia/uploads:/app/media
```

Keep the existing `env_file` and add the following keys to the server-side `.env` if they are not already present:

```dotenv
MEDIA_ROOT=/app/media
MEDIA_PUBLIC_ORIGIN=https://api.banxia.xin
```

Do not replace the existing `.env` file with `.env.example`.

## Deploy sequence

1. Back up `compose.yaml`, `.env`, and the current backend source.
2. Create the host media directory.
3. Add the bind mount to the API service only.
4. Rebuild the API image so Pillow and python-multipart are installed.
5. Recreate only the API service; do not recreate or remove the PostgreSQL data volume.
6. Verify `/health`, then upload a test image from the admin media library.
7. Confirm the original and `thumb-*.webp` files exist under `/var/lib/banxia/uploads`, and the image URL is reachable through `https://api.banxia.xin/media/...`.

The upload endpoint accepts JPEG, PNG, and WEBP images up to 4 MiB each. SVG and other formats are intentionally rejected. Files are decoded and re-encoded before storage; filenames are generated by the server. Deleting an asset is blocked while a content item references its URL.

## Rollback

If the new API fails to start, restore the backed-up backend source and Compose file, then rebuild/recreate only the API service. Uploaded files in `/var/lib/banxia/uploads` are independent of the application image and should be retained.
